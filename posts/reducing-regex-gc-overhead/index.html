Reducing Regex GC Overhead

Nov 20, 2026

In this post, I am going to talk about an optimization I made in the .NET regular expression library that reduced full-GC time by 75% or more in node-heavy stress cases.

Scenario

Back when I was working on the garbage collector, I fixed a bug in the mark stack overflow handling. That work introduced me to an unusual GC code path.

During the mark phase, the GC performs a depth-first-like traversal of the object graph to discover live objects. This requires a mark stack to remember objects whose references still need to be examined.

A sufficiently deep or highly connected object graph can exhaust that stack. The GC must then recover through a retry process to ensure that every live object is eventually marked. Suffice to say, this path is not fast, nor is it a path we intend to optimize for regular use.

As I remember it, the bug was exposed by a regex stress test. At the time, I thought that this was a situation the library could avoid by using a better representation. Instead of retaining a large graph of individually allocated and linked objects, it might store the same information more compactly.

I made a mental note to investigate it when I had the opportunity. It took a few years, but eventually I did.

The object graph

The .NET regular expression library has a NonBacktracking engine. Internally, it converts the expression into a symbolic representation and lazily constructs matching states as it processes input.

The symbolic expression was represented by SymbolicRegexNode<TSet> objects. Each node contained its data and references to its child nodes.

SymbolicRegexNode object
|-- Left  -> SymbolicRegexNode object
|-- Right -> SymbolicRegexNode object
`-- Node data

The nodes were interned, so structurally identical expressions shared the same node. This made the representation a directed acyclic graph instead of a tree, which is important for avoiding even more nodes.

Still, complicated expressions could retain more than 100,000 node objects. During a full GC, the collector had to mark every object and follow every reference between them. Even if the total retained memory was not enormous, the number of objects and edges made the graph expensive to traverse.

This is a case where the shape of the retained data matters in addition to its size.

The arena idea

The nodes are immutable once constructed, and they already belong to a SymbolicRegexBuilder<TSet>. That makes them a good fit for an arena.

Instead of allocating every node as a separate object, the builder can store the node data in an array. References between nodes can then be represented by integer indexes.

SymbolicRegexBuilder
`-- NodeData[]
    |-- NodeData { LeftId, RightId, ... }
    |-- NodeData { LeftId, RightId, ... }
    `-- ...

SymbolicRegexNode<TSet> = 4-byte node ID

The new SymbolicRegexNode<TSet> is a four-byte value-type handle. ID 0 represents a null node, and positive IDs locate immutable NodeData records in the builder.

This replaces a large graph of objects and references with a small number of arrays containing value data and integer links. The GC still needs to retain the arrays, but it no longer needs to visit every symbolic node as a separate object.

IDs need an owner

An integer by itself is not enough to identify a node. The same ID can refer to different nodes in different builders.

Operations on a node therefore also need the owning builder. A temporary SymbolicRegexNodeContext<TSet> carries the builder, an array snapshot, and the current node ID.

The context is used while traversing or operating on the symbolic graph. When it visits a child, it reuses the same array snapshot and changes only the ID. This avoids repeatedly locating the arena for every field access.

Matching states remain objects because they contain other state needed by the matcher, but they now retain a node ID instead of a node object. Frequently used properties such as nullability and state flags are computed when the state is created, so the warmed matching loop does not need to repeatedly access the arena.

Growing the array

The symbolic graph is constructed lazily. The arena therefore needs to grow while matching states may already be reading it.

A normal List<NodeData> is not sufficient for this. It does not expose a stable backing-array snapshot, and its publication order is not designed for concurrent readers.

The arena publishes a node in this order:

  1. Construct the complete immutable NodeData.
  2. Store it in the current or replacement array.
  3. If the array grew, publish the replacement array.
  4. Publish the new node count.

Readers acquire the node count before capturing the array.

Children are always published before their parent. Therefore, any array containing a parent also contains its complete subtree. If a reader keeps an old array after the arena grows, that old array remains a valid immutable snapshot for every node it could previously observe.

This publication scheme was one of the less obvious parts of the change. Replacing references with indexes is simple. Making those indexes safe while the arena grows requires preserving the ordering guarantees that the old object graph naturally provided.

Measuring the object-heavy case

I used two stress patterns that construct approximately 125,000 symbolic nodes while matching a 50,000-character input.

(?:a|AA|BCD).{20}$
(?:a.{20}|a.{10})bc$

The regex and input were retained, and I measured 15 forced full GCs in each process. Each result below is the median of three independent processes.

The reduction in GC time is much larger than the reduction in retained memory. This is the result I was looking for. The important difference is not only that the arena uses fewer bytes, but that the GC has far fewer objects and reference edges to traverse.

Representative expressions

The stress cases demonstrate the GC problem, but most regular expressions are much smaller. I also measured representative Email, URL, and IPv4 expressions.

Email -0.5% +0.1% -1.9%

Negative values indicate improvement.

Warmed matching remained approximately neutral. Small expressions also do not receive a meaningful memory improvement because they do not retain enough symbolic nodes for the object graph to dominate.

The first surprise

Changing the representation exposed a browser WebAssembly stack regression.

One symbolic operation recursively counted singleton nodes. The old nodes were small object references, while the new traversal carried a larger context containing the builder, array snapshot, and node ID. The algorithm had not changed, but each recursive frame became more expensive.

The fix was to replace that recursion with an explicit traversal.

This was an interesting reminder that reducing GC-visible objects does not automatically reduce every kind of memory usage. Moving information from an object reference into a temporary context can change native stack usage even when the logical operation is the same.

The second surprise

During review, a benchmark with 12 nullable captures exposed a warmed Match regression.

After a successful capturing match, the engine applies capture effects from a nullable end state. The implementation recursively followed several tail paths. As with the WebAssembly issue, the larger node context made those recursive calls more expensive.

The traversal was changed to recurse only for the non-tail left side of a nullable concatenation. It iterates through right children, selected alternatives, loop bodies, and wrapper nodes.

A same-machine comparison before and after this fix produced:

Input Initial arena change Updated traversal Change
"" 1,377 ns 851 ns -38%
"x" 1,330 ns 876 ns -34%

Allocations remained 968 bytes, and the corresponding warmed IsMatch controls remained approximately neutral.

This regression would have been easy to miss by measuring only construction, IsMatch, or the node-heavy stress case. Reviewer benchmarks covering a different API found it.

The cold-path tradeoff

The 125,000-node stress cases showed a variable one-time construction and first-match regression. Across independent processes, the slowdown ranged from approximately neutral to 30-37%, or roughly 100-200 milliseconds.

CPU traces showed that most of this time was additional JIT compilation and generic code expansion in the symbolic engine, rather than arena resizing or warmed node access.

Metric Objects Arena
JIT compilation events approximately 908 approximately 3,413
Generated native code approximately 324 KiB approximately 909 KiB

This is runtime JIT compilation of the generic symbolic engine. It is not generated or compiled regex code. Repeated constructions in the same process do not continue paying the full cost, and warmed matching remains neutral.

I experimented with reducing inlining. It reduced generated code size, but it did not improve the end-to-end cold time, so I did not keep that change.

Regexes are often constructed once and reused. A lexer may retain its regexes throughout parsing, including time spent waiting for I/O. A server may retain validation regexes for its entire serving lifetime. For large symbolic graphs that survive repeated full collections, the additional construction cost is paid once, while the reduced tracing cost benefits every subsequent full GC. That is why I consider this tradeoff worthwhile for long-lived, node-heavy expressions. Small expressions and short-lived, one-shot uses may not benefit.

Scope

The optimization applies only to the symbolic representation used by the NonBacktracking engine.

It does not change:

  • The parser’s short-lived RegexNode tree.
  • Backtracking regex execution.
  • Source-generated or compiled regex output.
  • Public APIs or matching behavior.

The final change is available in dotnet/runtime#136375.

Conclusion

This change started with a GC failure mode I encountered several years ago. The GC must correctly handle an overflowing mark stack, but a library can still avoid creating an unnecessarily difficult object graph for the collector.

The arena reduced retained memory by about 16%, but reduced forced full-GC time by 75-91% in the node-heavy cases. The difference shows why object count and graph shape can matter much more than byte count alone.

The work also produced two regressions caused by larger recursive traversal frames and a cold-path JIT tradeoff. Those results were useful. An optimization is not complete when the first benchmark improves; it is complete when we understand where the costs moved.

It took a few years to return to the regex stress case, but the original idea turned out to be practical: when many immutable nodes share one owner, indexes into an arena can be much friendlier to the GC than a large graph of individually allocated objects.
